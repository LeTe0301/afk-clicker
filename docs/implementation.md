## Root cause
G#8, round 1 diagnosis (still correct as far as it went): `apply_hotkey()`'s not-permitted branch assigned `self.registered_hotkey = self.hotkey` even though no listener was started in that branch (starting one there would trap the process, which is exactly why the branch exists). `registered_hotkey` is read elsewhere as "a listener is running for this" (`self.registered_hotkey.label() if self.registered_hotkey else ""`), so the assignment made the status pill/label claim a running listener that did not exist. The line immediately below it (`self.hotkey_label.config(text=self.hotkey.label(), fg=INK)`) was already dead: `self._hotkey_error(...)`, called on the very next line, unconditionally overwrites `hotkey_label` again via its own `self.hotkey_label.config(text=HOTKEY_HELP, fg=BAD)`.

G#8, round 1 fix was **incomplete**: it removed the bad assignment but relied on `registered_hotkey` merely being *left alone*, reasoning (per the spec's own "Proposed approach") that it would already be `None` at that point. That's only true for a *first-ever* Apply. On a *second* Apply while still not permitted — after an *earlier successful* Apply had set `registered_hotkey` to a real `Hotkey` and started a listener — `self.hk_listener` is correctly `.stop()`ped and cleared to `None` a few lines above the permission check, but nothing in the not-permitted branch touched `registered_hotkey`, so it kept the stale `Hotkey` from the earlier successful Apply. That is G#8's exact bug ("`registered_hotkey` claims a listener that is not running"), reproduced live by the reviewer. Round 2 fix: explicitly assign `self.registered_hotkey = None` in that branch, so both the first-Apply and subsequent-Apply cases land on the same correct state, regardless of what `registered_hotkey` held coming in.

G#9 items 1–2: `selftest()` guarded `kb.Listener(on_press=...)` construction with `if macos_input_permitted():`, but per `macos_input_permitted()`'s own docstring ("pynput does not reliably raise... on a machine that has never granted it, creating the CoreGraphics event tap can abort the process... AXIsProcessTrusted answers the question without touching the event tap") the crash risk is in `.start()`ing a listener (creating the event tap), not in constructing one. `selftest()` never calls `.start()`. The guard therefore bought no real-Mac safety while costing CI coverage of the unconditional-construction path, since `AXIsProcessTrusted` reports trusted on `macos-latest` and the `if` branch was always taken there anyway.

## Key decisions / tradeoffs
- Kept the single remaining `macos_input_permitted()` call in `selftest()` rather than removing it too. Its own inline comment (`# the guard itself must load`) states its purpose is to exercise the guard's ctypes/import path in CI independent of listener construction — that purpose is unaffected by dropping the `if`, so it is not redundant, just no longer paired with a conditional.
- G#8's fix assigns `self.registered_hotkey = None` explicitly rather than relying on "don't touch it." This is a one-line difference from round 1 but changes the invariant from "correct assuming the caller's prior state was already `None`" to "correct unconditionally" — the latter is what `registered_hotkey`'s own contract ("a listener is running for this") actually requires.
- Left `self.hotkey` completely untouched by the G#8 fix in both rounds (no assignment added or removed) — verified by re-reading the branch before and after, and by two separate sabotage checks (round 1's single-Apply case and round 2's second-Apply case) that both fail the right way if `self.hotkey` is cleared there.

## Deviations from spec
- **`docs/spec.md` itself was wrong** in its "Proposed approach" → G#8 section and its "Edge cases" → "Re-Apply while still not permitted" bullet: both asserted that leaving `registered_hotkey` unassigned in the not-permitted branch is correct in *both* the first-ever-Apply and the re-Apply-while-still-blocked cases. That's false for the case where an *earlier successful* Apply had already set `registered_hotkey` and started a listener — the reviewer reproduced this live in round 2. Both sections of `docs/spec.md` have been corrected in place with inline "Correction (round 2, post-review)" notes explaining what was wrong and why, rather than silently rewriting history.
- **`tests/test_hotkey.py` needed one line beyond what the spec's proposed diff showed: `import ctypes.util` at module top.** The spec's item-5 rewrite (patch `ctypes.util.find_library`, then fake `sys.platform = "darwin"`) fails on this Linux sandbox as written, with `AttributeError: module 'ctypes' has no attribute 'util'` raised from inside `unittest.mock.patch`'s target resolution (`pkgutil.resolve_name`). Root cause: `ctypes.util` is not imported anywhere in the process before this test runs (it's only ever imported lazily, inside `macos_input_permitted()`, and only on real darwin). `pkgutil.resolve_name("ctypes.util.find_library")` tries `importlib.import_module("ctypes.util")` to resolve the dotted path — and `ctypes.util`'s own module-level code branches on `sys.platform`, so importing it for the first time *after* the test has already faked `sys.platform = "darwin"` fails partway through (caught internally as `ImportError` by `resolve_name`, which then falls back to plain `getattr(ctypes, "util")` and gets `AttributeError` since the submodule was never actually bound). Confirmed by reproducing both ways directly in the venv: faking `sys.platform` before any import of `ctypes.util` reliably breaks `pkgutil.resolve_name`; importing `ctypes.util` first (under the real platform), *then* faking `sys.platform`, does not. Fix: import `ctypes.util` eagerly at the top of the test module, before any test has a chance to fake `sys.platform`. This is additive test-infrastructure only — it does not change the test's assertions, the patch target, or the production code the spec specified, and does not affect real-darwin runs (there `sys.platform` is never faked, so the ordering issue never arises).
- **New test added beyond the spec's explicit test list** (round 2): `test_registered_hotkey_cleared_on_second_apply_without_permission` in `tests/test_ui.py`, per the reviewer's explicit instruction to cover the second-Apply sequence. The original first-Apply test (`test_no_listener_is_started_without_permission`) is unchanged from round 1 and kept as-is.
- No other deviations. All five G#9 items and the G#5 evidence writeup match the spec's proposed diffs verbatim.

## Known limitations
- **G#9 item 1 (`selftest()`'s now-unconditional `kb.Listener(...)` construction) can only be confirmed safe on a real, permission-less Mac by the next `macos-latest` CI run**, not by this Linux/Xvfb sandbox. The reasoning (construction alone doesn't create the CoreGraphics event tap; only `.start()` does) rests on `macos_input_permitted()`'s own docstring and the PR #3 precedent cited in the ticket, not on a fresh macOS execution in this session.
- **G#9 item 5's rewritten test's real-darwin branch (the `if original_platform != "darwin":` no-op path, i.e. running with `sys.platform` already `"darwin"` and no fake needed) is only exercised structurally here, not on a real Mac.** Locally this session only exhausts the off-darwin path (Linux, via the `sys.platform` fake). Confirmation that the test passes when it *doesn't* need to fake the platform at all, and that `unittest.mock.patch("ctypes.util.find_library", ...)` correctly forces the fail-closed branch against a real, already-loaded `ApplicationServices` framework, is deferred to the next `macos-latest` CI run on this branch — per the spec's own Risk/rollback notes.
