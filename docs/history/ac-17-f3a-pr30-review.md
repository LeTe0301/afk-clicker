### 2. A `_ui_queue` swap during `_rebuild_ui()` can permanently drop an `ERROR`/`STOPPED`/`EATING` status update that isn't RUNNING/OFF — should-fix, reproduced, narrow
- File: `afk_clicker.py:1672` (the queue swap) and `afk_clicker.py`'s `_build_ui()` tail (the `if self.running: ... else: ...` resync, only ever writes RUNNING/OFF).
- Issue: documented as "harmless — the next state transition re-queues one," which holds for RUNNING/OFF (the only two states the rebuild's own tail resyncs) but not for a status text the tail never rewrites. Reproduced directly: an `("ERROR", BAD, "boom")` item queued into the pre-swap queue, with `running` already `False` (matching `loop()`'s own `finally` ordering), is silently dropped by a rebuild — the post-rebuild pill reads bare `"OFF"`, with no trace that the clicker actually crashed.
- Failure scenario: the click loop throws an exception (`self.mouse.click()` failing, say) in the same narrow window a user happens to click a theme/settings/game-nav control — the worker's `self._ui(self._set_status, "ERROR", ...)` call lands in the queue an instant before `_rebuild_ui()` swaps it. User sees a plain "OFF" pill with no indication anything went wrong. Same applies to an auto-stop `"STOPPED"` message and an `"EATING"` update landing in that window (the latter already independently tested and shown fixed for the *common* window by `QueuedStatusSurvivesARebuild` — but that test targets the window *before* `self.status` is reassigned, not this queue-drop window, which is a different, earlier point in the same rebuild).
- Not a blocker: requires the race to land in a sub-millisecond window between a worker `_ui()` call and the main thread's queue swap, and the safety-relevant part (the clicker actually being stopped, `self.running`) is never lost — only the specific reason text is. Reasonable follow-up: have the tail resync the full last-known status text/color/hint (not just a running/not-running boolean), or snapshot+replay the old queue's contents into the new one before dropping it.

### 3. `Store.save()`'s existing silent-`OSError` swallow lets the displayed theme and the on-disk value disagree under a read-only config dir — pre-existing pattern, not new, not blocking
- File: `afk_clicker.py:850-858` (unchanged by this diff).
- Reproduced directly with a real `chmod 0500` on the config directory mid-session: `_apply_appearance("light")` visibly repaints the window and updates `store.data["appearance"]` in memory, but the on-disk file's mtime/content never change, and a subsequent fresh `Store()` read of the same file still resolves to `"system"`.
- Not a regression this PR introduces (every `Store` key shares this exact fire-and-forget save behavior), but Appearance is the first key where a failed save is *immediately visible* as a contradiction on screen rather than only surfacing on the next restart. Flag for a future persistence-hardening pass — out of 3a's explicitly-scoped Non-goals (no schema/persistence rework).
